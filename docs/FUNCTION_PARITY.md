# Lulu 功能对等迁移清单

## 文档解释优先级

1. `docs/MIGRATION_PLAN.md` 是迁移范围与页面取舍的最终标准。
2. 计划明确写“原原本本迁移／功能迁入／保留”的能力，必须完整迁入，不能用占位页或自行重做的简化版替代。
3. 计划明确写“重写”的页面，只重写视觉与组织结构，旧业务能力、数据和失败路径仍须迁入。
4. 计划明确写“空页面／暂不迁入／删除／隐藏”的内容，必须按计划保持为空或移除，不得为了追求表面完整擅自恢复。
5. 其他对等文档与计划冲突时，以主人最新确认和 `MIGRATION_PLAN.md` 为准。

## 硬性原则

1. `lulu/master` 是计划内功能的来源基线，`lulu1/main` 必须达到计划内功能零丢失。
2. UI、导航和页面视觉可以按计划重做，但任何被计划要求保留的业务能力、数据、设置、玩法、历史记录、角色交互与失败路径都不能擅自删除。
3. 新增功能只能作为增量保留，不能替代旧功能，也不能填充计划明确要求留空的页面。
4. 某个 App 只有在旧功能逐项核对、数据迁移、入口接入、主要交互可用且构建通过后，才能标记为“完整迁移”。
5. 未核对完成的模块必须标记为“部分迁移”或“待核对”，禁止使用“完整迁移”表述。

## 验收状态定义

- **未迁移**：新仓库没有计划要求的该能力。
- **部分迁移**：已有入口或部分规则，但不具备计划要求的完整能力。
- **功能对等**：计划要求保留的旧功能、主要数据、入口和交互已保留。
- **增强完成**：在功能对等基础上增加新能力，且没有填充计划明确要求留空的内容。
