## 一、每次接力执行协议（含每小时自动开发）

1. **刷新**：先读最新 main 的 AGENTS.md、CODE_INDEX.md、本页、专项进度最近记录，以及所涉源码/测试/Actions。旧记录里的 pending、cancelled 和 failure 不等于最新提交的结论；当前安装版与 GitHub main 分开判断。
2. **选任务**：顺序选择第一个尚未完成、当前工具能实做的稳定子步骤（ID.数字）。先判定「已验通 / 已实现待验 / 已证实缺口 / 待测量」，不重做完成项。遇到真机/真实模型/用户日志才可验证的项目，标清外部待验，**转下一个能实施的源码或回归子步骤**，不能空转一小时。
3. **调查根因**：追入口 → 人物/数据权威 → 决策与执行 → 真实结果 → 持久回执与下轮；区分配置、源码、测试、第三方、设备。不要加关键词代决策、影子 Store、固定台词、重复收费模型调用来伪装活人感。
4. **真实交付**：原则上每轮完成一个最小可验证的源码或回归工作包；必要时完成关联改动；只改既有 main，先刷新避免并行覆盖。仅修改大纲或创建 Issue 不是功能修复。没有可证代码缺陷时允许补测量/诊断，但不能为了凑提交而改写无关源码。
5. **验收分层**：源码提交、JVM 测试、Android APK/发布、真机、真实模型、跨日是不同层级；分别记录 SHA、运行 ID、状态和缺失证据。取消/失败/运行中的 CI 不可勾成功；旧安装包不能冒充新版本体验通过。
6. **交接**：完成子步骤勾 [x]，把证据追加到专项进度；只剩外部验收的项目保留具体待验子步骤，不保留已完成开发流水。每轮报告改了什么、为何、提交和测试结果、下一编号。不重用 ID；有新根因则在原 ID 下新增子步骤。
7. **并发与授权**：多窗口/自动任务先核 main 与同文件 SHA；有冲突时刷新或避让，不强推、不覆盖用户改动。真实模型和真机证据无法拿到时写「未知」，不能编造，也不能把私人日志提交公开仓库。
