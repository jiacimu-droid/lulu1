# 自主行动连续性：统一主角与居民的逐动作执行（2026-10-26）

对应研究清单第5项（计划跟进）、第6项（真实世界行动），延续第16项的长目标/协作方向。属于既有架构的工程修复，不表示移植了新框架、完成整个项目或提高底座模型智力。

## 根因与处理

1. 主角 `performAction` 的既有暂停联系/未回应联系节流，原本直接退出整个决定，吞掉同轮独立发圈、探索等步骤。现在限制移至 ToolRouter 的新执行边界，主动作与副动作共用；被拒联系留下原执行器的拒绝回执，独立步骤继续，依赖步骤等待实际成功。没有降低原联系限制、从沉默推断新拒绝或新增强制联系规则。真实新用户回合仍用原回复入口。
2. ToolRouter 先恢复原真实回执，再检查新尝试的联系边界；后来暂停联系不能把过去已经送达的消息改写成失败，更不能为恢复旧结果重复发送。目标定时复盘标记从原调度适配器贯穿到副步骤，仍不替模型分配目标。
3. 居民附加动作原有另一个简化循环：不处理 requiresPreviousSuccess，丢掉 motiveId/concernId/experienceId/reason，并静默截断到8步。现在只适配参数/场景允许集合，交给原 OrderedCharacterActions，统一处理实际完成、独立继续、依赖停止、别名、因果关联和回执。模型输出仍受原生成预算/能力权限约束，没有强制动作数量或额外模型轮次。
4. 保留居民历史 `$turnId-extra-$index` 执行ID；升级后同一动作仍恢复旧回执，避免换ID导致二次发圈/发送。附加动作继续剥离原计划planId与用户回复证据，不能冒充原日程完成。
5. 居民原计划执行前的重复 canBegin 校验可能在思考期间计划被撤销后直接退出，吞掉独立步骤。现在唯一实际执行检查由原 ToolRouter→RoleDayScheduleStore 承担，拒绝有证据，后续依赖首步仅在原活动真正完成时开放；等待、取消、改期不等于原活动已完成。

## 资源、数据与验证

未新增人格/动力/记忆/任务 Store，没有迁移或清空历史，没有提高默认模型频率；仅复用原一次决定和独立工具回执。旧主角步骤ID保持默认不变，居民步骤继续使用原ID。

回归覆盖明确暂停联系、两次未回应联系节流、独立生活仍执行、副步骤不能绕过联系限制、旧送达回执重放；居民依赖失败/场景拒绝后独立继续、9步不丢失、每步动机关联、planId隔离，以及真实模型请求期间取消原计划的竞态。MockWebServer 仅验证本仓协议与控制链，不代表真实模型会更主动。

Android单测、APK构建以原 release 工作流结果为准；真机后台时机、多日主动频率、社交内容质量仍需使用反馈。
