# 露露机统一人物因果架构 · 永久开发契约

> **必读（与 AGENTS.md 同级的架构约束）**。用户多次确认：这是适用于任意人设、任意性格与任意场景的公共基础架构。单个角色的聊天反馈不能授权修改全体角色的性格、说话习惯或关系边界。该文档用于约束以后每次跨窗口开发；文档不是「所有能力已经验收」的声明。

## 一、不可变的主循环

```text
现实输入/已发生事件
  ├── 用户私聊/群聊/电话/语音/图片
  ├── 数字世界/居民交互/阅读/游戏/外部设备结果
  └── 时间、活动计划到期、既有目标复查、任务回执
              │
              ▼
  统一事实与原始时间线（SharedExperienceTimeline；权威证据、场景归属、时间、来源ID）
              │
              ▼
  同一个人的上下文：身份与稳定核心人格 + 当前关系网络
                     + 相关经历/记忆/学习 + 此刻心理/目标与现场事实
              │
              ▼
  感知 → 召回 → 本人的理解 / 意义判断 / 评估
              │
              ▼
  心理：情绪、念头、主观印象、矛盾、挂心、motives
              │
              ▼
  本人的一次「自主选择」，可产生 0 / 1 / N 个行动或未来安排
         ┌────────────┬────────────┬────────────┬───────────┐
         ▼            ▼            ▼            ▼           ▼
        说话         沉默         工具/活动    日记/收藏    未来计划
         └────────────┴────────────┴────────────┴───────────┘
              │ 每个选择独立身份、顺序/条件、权限和来源
              ▼
  各动作交给已有 ToolRouter / 消息、通话、世界、任务执行器
  「决定」≠「已执行」≠「已产生结果」≠「用户满意/目标完成」
              │
              ▼
  分别写入实际回执（成功/失败/进行中/取消/未证实、发送证据和错误）
              │
              ▼
  更新统一时间线 → 主观反应 / 记忆 / 关系 / 挂心进度 / 知识 / 成长
              │
              └────────→ 下一轮同一角色、同一架构的上下文
```

- **这个循环不可被页面、场景或某个角色另起一份复制品**。手机保存连续状态，API 按需做理解、判断、选择和自然表达；不增加强制的付费模型回合，仅为了满足某个字段。
- 私聊、群聊、电话、见面、数字世界、主动感知、学习、阅读及计划到期，是不同的 **入口适配器**，不是不同人物或独立人格。
- 群聊按各参与角色依次独立调用其自身模型与上下文；同一轮群内前人的已送达消息才是后人的可见事实。
- **多行动不是多个人格**。同一次主决策可说一句话、播放音乐、再写日记，也可决定先安静、晚些继续、拒绝或取消。动作不互斥；「回复」不属于工具的附属物。
- 单次动作执行所需权限与安全限制由原执行器负责；模型主动说明「想做」「已决定」不能冒充执行成功。
- 模型可以决定先后、是否依赖前一步的结果，以及未来再做；持久未来行动必须落到现有持久任务/日程引擎，不能靠在电话或聊天里承诺后临时 delay，也不能默认按时执行。
- 表达层只能渲染本角色已选定要说的内容，不得擅自重做心意、强制所有角色回复、用固定歉词代替本人表达、也不能将未说出口的私有分析念给用户。
- **沉默是合法选择**；但执行一个工具绝不自动表示用户消息已经得到回复。实际发送、主动决定暂不回复、未执行/失败要分开记录；未实际送达的答复不可标为已送达。

## 二、人格的归属：个体 vs 公共

| 用户提出的变化 | 默认允许修改的范围 | 禁止的偷换 |
|---|---|---|
| 「江渡这句话太啰嗦／总觉得我嘴硬／相处方式不对」 | 江渡本人的人格、表达偏好、当前关系、已有事实支持的主观状态与既有用户自定义设定 | 修改所有角色的共同道歉模板、统一温柔口吻、身份/关系范式或硬编码特殊称呼 |
| 「某角色读书感想不自然」 | 对该角色的风格和真实阅读背景进行具体排查；公共功能有客观缺陷再修公共层 | 因一个角色的文学审美强制全体角色喜欢刺激、热情或暧昧 |
| 「任何角色执行工具就不回消息」「消息被读了却没有回复回执」 | **公共执行契约或路由的真实 BUG**，可修公共层，增加泛化测试 | 用独属于江渡的提示词补丁掩盖消息/动作互斥的系统缺陷 |
| 用户明确要求全体生效的公共能力（权限、追溯、计时、统一记忆） | 对应共同执行和数据层；依然保留各角色自选行为 | 把「能力存在」升级成「每个人必须使用」 |

**编辑某角色的规范**：
1. 先辨别用户是在评价**某人**还是报告**所有角色通用机制**故障；若明确点名或提供单角色对话，默认只改其个人配置/关系与状态。
2. 尊重用户自行编辑的人设和关系，不能未经授权覆盖原文、空值或把一个人的亲密关系强加给别人。
3. 公共提示词只约束真实性、执行权限、回执和证据，不规定喜欢谁、是否撒娇、称呼方式、道歉句式、语音口吻、情绪强度等角色差异。
4. 长期人格改变可从真实多次经历积累，核心身份、价值与用户显式设定变化谨慎；一次新闻、一次读书或一次猜测不足以强制永久人格更新。

## 三、已有唯一权威来源（严禁新造影子轮子）

- 原始事实与执行证据：`SharedExperienceTimeline`；删除/撤回原始来源，应同步使依赖的主观投影和成长结论失效。
- 本人的定义、核心人格与关系：现有角色配置/`CharacterRuntime` 与唯一关系网络；不是另一套 roleProfile 或「只供电话」性格。
- 当下心理、长期想做的事与挂心：`CharacterInnerLifeStore`（唯一 `motives` 权威）、既有挂心和人格投影；不能为了工具动作新增「动力库」。
- 记忆、学习、成长：复用现有召回、`CharacterLearningLedger`、成长投影；日记是独立主动写作，不是心声/时间线自动备份。
- 实际行动：`ToolRouter` → 对应已有专门执行器，幂等请求 ID + 独立回执；`CommitmentTaskStore`、原个人日程执行器处理未来行动。
- 模型/场景入口：统一角色上下文与网关；`ProactivePerceptionRuntime` 为上线新消息常用入口，`LuluDeviceToolBridge` 为前台/电话适配器；差异仅是 IO、低延迟、UI 和设备资源，不可分叉人物心理真相。
- 可能存在遗留的同义 `intention` / `motiveId` / `pendingConcern` 字段，应保持兼容和收敛，不得借任务新增平行角色人格、记忆或行动中心。

## 四、一次模型决定、多项行动的明确契约

典型意图：角色听见用户要求调大音乐，决定「先回一句，再把音乐调高，之后写一条自己的日记」。

一个结构化角色决定可以包含：其 **主要回应/态度** 与多项 **副动作**。这些动作是其本人一次判断的组成部分，但由各执行器分别完成，并分别返回不同结果；无须再调用第二个「代替他判断如何回复」的人格模型。

```json
{
  "action": "message",
  "text": "等一下，我把声音往上调一点。",
  "sideActions": [
    {"tool": "control_volume", "args": {"action": "adjust", "deltaPercent": 10}},
    {"tool": "write_journal", "args": {"title": "这一刻", "content": "刚才的音乐让我想起..." }}
  ]
}
```

这是结构示例，不代表模型必须每轮回话、记日记或执行两项动作。实际副动作必须有独立请求 ID 和授权；`write_journal` 的内容必须是角色实际选择写下的文字，不由执行器拼一份日记。多步依赖须严格尊重声明的先后与真实结果；默认完成「消息发送」不意味着音量设置成功，反之亦然。对用户是否回应，只看真实发言或明确选了沉默，不以任何其他工具成功为依据。失败要留具体回执，不能被后续动作遮盖。

**跨窗口开发验收用例（必须保持）**：
- A 人格和 B 人格对同一情境作不同决定，不得被公共补丁统一成一种性格。
- 角色决定「仅用工具」时不伪造回复；未选择沉默时不能把用户消息静默吞掉。
- 同轮「回复 + 调音量」、「回复 + 写日记」、三项组合：各动作只执行一次、每项独立回执、成功失败互不冒充。
- 用户追加新消息仍能触发新感知，不因旧五分钟在线租期/工具结果阻断回复。
- 电话语音、字幕、聊天不公开 `innerThought`、工具原始协议和内部分析。
- 同一人的新关系/情绪/学习结果被后续私聊、电话与自主活动共同召回；另一人的记忆不串入。
- 原事件被删、被撤回或执行失败时，不得凭对应投影虚构成长。
- 计划/承诺跨重启仍有效；未到期、已取消、未确认和已完成严格区分。

## 五、修改前的强制核对

1. 先读仓库根部 `AGENTS.md`、本文件与 `COMPANION_GROWTH_FRAMEWORK.md`；再按 `CODE_INDEX.md` 找**现行**入口。
2. 先写清「这是某角色的审美/性格问题，还是公共执行契约错误」；前者默认**不得修改** `CharacterDecisionProtocol`、统一模型网关或全角色提示词。
3. 涉及认知/行为时检查从感知→决策→执行→证据→下一轮召回的全链，**不只是截图中的一句话**。
4. 不能因新工具加入而修改主链为「选择一个动作→其他行为丢弃」；新增能力仅扩展执行器和行动清单。
5. 引入新状态或 Store 之前明确为何现有唯一来源不足；如无必要一律复用。
6. 测试证明普通聊天能发消息、工具能执行、两者同回合可并存，旧数据与用户定义人物不被改写。
7. 静态检索、单测、APK 构建、真机、多日连续体验分层报告，不能相互冒充。

如开发者认为需要修改本主循环，须先明确向主人提出影响和迁移方案，取得**针对架构本身的确认**；不能把单角色聊天反馈当作改架构授权。
